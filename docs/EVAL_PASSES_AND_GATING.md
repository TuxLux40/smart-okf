# Eval / Acceptance Spec — Pass architecture, gating, navigation

Formalizes the requirements captured in the two design messages that produced this file.
Each item is a testable acceptance criterion. "MUST" = required for the feature to be
considered done; "SHOULD" = strong default, overridable by config; "MAY" = optional toggle.

## 1. Pass architecture and terminology

The pipeline has exactly four passes, named by verb, producing named artifacts. This
naming MUST be used consistently across code, config keys, CLI flags, prompts, SKILL.md,
README, and DESIGN.md — no synonyms ("summary pass", "deriver", "reasoning") outside of
historical changelog entries.

| Level | Pass (verb) | Artifact | Location |
|-------|-------------|----------|----------|
| 1 | `extract` | transcript | `.okf-transcripts/<file>.txt` |
| 2 | `derive` | facts | inline in the aggregate section by default; per-file file only when toggled |
| 3 | `aggregate` | aggregate | `<folder>.md` (`type: FolderSummary`) |
| 3b | `roll-up` (mode of aggregate) | index | parent `<folder>.md` links child aggregates |
| 4 | `dream` | matter + synthesis | `matters/<slug>.md`, `synthesis.md` |

**Assertions**
- A1. Every config key / CLI flag / prompt filename introduced or renamed uses one of
  `extract` / `derive` / `aggregate` / `roll-up` / `dream`.
- A2. `roll-up` is a mode of `aggregate`, not a separate pass (no standalone `roll-up`
  script or service module).
- A3. `dream` remains global across the whole tree (already cross-folder); it is not
  affected by the `aggregate` recursion/roll-up setting.

## 2. Level 2 `derive` — always on, writing into the aggregate; per-file artifact opt-in

`derive` is a first-class pass that always runs: derived facts (contacts, addresses,
contract/customer numbers, dates, amounts) MUST be extracted and written into the folder
aggregate, where they are directly usable. What is opt-in is only the *standalone per-file
fact artifact* — the user does not want a file per document by default.

**Assertions**
- B1. `derive` runs on every ingested document by default and writes derived facts into
  that document's aggregate section. It is not toggleable off (facts in the aggregate are
  the point of the pipeline).
- B2. A config toggle (e.g. `derive_per_file: bool`, default `false`) — the *only* thing
  that is opt-in here — MAY additionally emit one facts file per source document to a
  dedicated, clearly named location (`.okf-facts/<file>.md` proposed), never mixed into
  the document tree as visible siblings of the originals.
- B3. The per-file code path MUST be exercised by a test and produce valid OKF output when
  the toggle is on — a dormant-but-broken opt-in path is not acceptable.
- B4. Turning the per-file toggle on/off MUST NOT change the facts already merged into the
  aggregate (the per-file file is additive, not a replacement).

## 3. Level 3 `aggregate` — roll-up is core behaviour, not optional

Deep trees (`health/2026/befunde/`) otherwise produce many small isolated aggregates with
no connection to their parent. Roll-up is a core part of the archival value (Findbuch /
tektonik: every level of the hierarchy has a description that points down into the next),
so it is standard behaviour, not a toggle.

Best-practice constraint (archival findmittel / MOC pattern, from the
`dokumenten-organisation` skill's Findbuch-Prinzip): a parent MUST NOT re-summarize child
full text. It links child aggregates plus a thin synthesized overview of what lies
beneath. Children stay canonical; incrementality is preserved.

**Assertions**
- C1. `aggregate` produces one aggregate per folder AND, for any folder with subfolders,
  a roll-up section in the parent's `<folder>.md` linking each child aggregate with a
  one-line overview. This is the default and only behaviour — there is no flag to disable
  roll-up.
- C2. A parent roll-up MUST NOT re-extract or inline child document text; it is a link
  list plus a short synthesized overview (Findbuch-Prinzip: register, not duplication).
- C3. Roll-up MUST NOT trigger re-extraction of unchanged children (hash incrementality
  holds); only the parent index is (re)written when a child aggregate changes.
- C4. Roll-up (hierarchy index) and `dream` (cross-folder subject synthesis) are distinct
  layers — roll-up follows the folder hierarchy (Provenienz), `dream` cuts across it
  (Pertinenz); neither implies the other.

## 4. Self-updating root README for human navigation

A human-facing `README.md` (or equivalent index) at the documents root, regenerated by the
pipeline, for browsing — explicitly aimed at Nextcloud users who see the folder in a file
UI. This is navigation + at-a-glance stats, not an OKF aggregate.

**Assertions**
- D1. A generated root navigation file lists top-level folders with links to their
  aggregates and a one-line description each.
- D2. It includes useful statistics (e.g. document count, folder count, last-ingest
  timestamp, number of matters, flagged/skipped counts) computed from the actual tree.
- D3. It is regenerated automatically as part of the normal pipeline run (self-updating),
  not a manual step.
- D4. It is human-readable in a plain file browser / Nextcloud preview (valid rendered
  Markdown, no raw dumps), and MUST NOT collide with reserved OKF filenames or be mistaken
  for an OKF aggregate (distinct name and/or clearly non-OKF frontmatter).

## 5. Ingestion gating — irrelevant, low-priority, and protected files

Trivial documents (manuals / Bedienungsanleitungen, terms of service / AGBs, boilerplate)
must not consume extraction or, especially, deep-analysis budget. Password-protected files
must be skipped safely.

**Assertions**
- E1. Onboarding asks the user which kinds of documents are irrelevant or low-priority
  (with sensible defaults offered: manuals, AGBs/ToS, marketing) and records this in config
  (e.g. patterns / folder rules).
- E2. Files matching an exclusion rule are not ingested at all (no extraction call), and
  the reason is logged as skipped.
- E3. Files that are neither explicitly excluded nor explicitly prioritized are eagerly
  **deprioritized** — automatically kept out of the expensive `dream`/deep-analysis pass by
  default (still extractable/aggregatable, just not deeply synthesized), rather than
  silently treated as important. "Eager" = the default leans toward deprioritization when
  priority is unknown.
- E4. Password-protected / undecryptable files are, by default, skipped (never
  half-extracted, never crash the run) and logged as skipped with a clear reason.
- E5. All of E2–E4 count toward the partial-success exit signal (exit code 2), consistent
  with existing skipped/flagged handling — a run that silently drops files must not report
  as fully green.

## 6. Archival principles — wired and formalized, chosen at onboarding

The archival/library-science principles that justify the architecture MUST be formalized
in this repo, sourced from the existing `dokumenten-organisation` skill
(`~/.claude/skills/dokumenten-organisation`, references `aktenplan-und-klassifikation.md`,
`retrieval-und-suche.md`, `spezialbestaende.md`) rather than reinvented — that skill is the
canonical statement of the methodology; smart-okf references and applies it.

Mapping (already implicit in the design, now made explicit):

- **Provenienzprinzip** (order by origin/context) → the `aggregate` + `roll-up` layer:
  documents keep the folder structure they arrived in; the hierarchy is described, not
  reordered. smart-okf never moves the user's files.
- **Pertinenzprinzip** (order by subject) → the `dream` / `matters` layer: cross-folder
  synthesis groups by Sachverhalt regardless of where files physically live.
- **Findbuch-Prinzip** (register points down, does not duplicate) → root README (§4) and
  roll-up (§3).

Where more than one principle could govern a decision, onboarding MUST ask rather than
assume.

**Assertions**
- G1. A doc in this repo formalizes the principles and cites the `dokumenten-organisation`
  skill as source (no silent copy of its text; reference + short applied summary).
- G2. Onboarding asks which ordering principle governs the user's tree / retrieval
  preference (Provenienz = respect existing folders as-is, the default and safest; vs.
  Pertinenz-leaning = lean harder on cross-folder matters), and records the choice in
  config so the passes can weight accordingly.
- G3. Whatever principle is chosen, smart-okf remains non-destructive to the source tree
  (it builds a knowledge layer on top; it does not rename or move the user's documents —
  that is the `dokumenten-organisation` skill's job, kept separate).

## 7. Cross-cutting: portability, modularity, customizability

Overarching goal from the same conversation: the skill must be portable, modular, and
customizable when a different user/agent invokes it.

**Assertions**
- F1. Core passes (`extract`, `derive`, `aggregate` incl. roll-up) always run and are not
  toggleable off — they are the archival baseline. Optional layers (`dream`, and the
  `derive_per_file` artifact) are individually toggleable. Every pass has its own
  model/host selectable and is independently runnable.
- F2. Onboarding asks: document location(s); which model for which pass; whether to run
  the optional `dream` layer now; and the governing archival principle (§G2) — then the
  run proceeds automatically to completion without further prompting.
- F3. End state per the user's archival goal: every ingested (non-excluded) document ends
  up with a transcript, a summary/aggregate presence, and derived facts, retrievable by any
  agent quickly and reliably without re-reading the original binary.
